# Migration file shape

Every migration in the wrangler-configured `migrations_dir` (default `migrations/`) is one `.sql` file (TAC-1402). The wrangler CLI is the applier and the D1 bookkeeping table (`migrations_table`, default `d1_migrations`) is the applied-state ledger. This asset shows the exact shape.

## Filename shape

The default wrangler pattern is `<zero-padded-integer>_<description>.sql`, generated by `wrangler d1 migrations create <database> <description>`:

```
migrations/
  0001_initial_schema.sql
  0002_soft_delete_column.sql
  0003_boot_markers.sql
  0004_notifier_schema.sql
```

The leading integer is monotonic across the directory; it anchors the applied-state ordering and the AC-13102-1 sequence check. The description is human-readable and appears in the file name and (by convention) the file header comment; it does not affect ordering.

Projects that pin an ORM override `migrations_pattern` on the D1 binding to match the ORM's filename shape (Drizzle's `0000_name.sql`, Prisma's `<timestamp>_name/migration.sql`). The leading-integer monotonicity property still holds; the pattern controls what the CLI matches, not the ordering discipline.

## File body shape

Each file body is engine-native SQL: one or more statements separated by `;`, terminating in `;`. Comments (`--` line comments) are allowed. The wrangler CLI executes the statements against the D1 database and records the applied file in the bookkeeping table.

Worked four-migration example (SQLite dialect, D1's native syntax):

`migrations/0001_initial_schema.sql`:

```sql
-- Initial schema for the domain.
-- Four tables: entityA, entityB, session, auditEntry.

CREATE TABLE entityA (
  id        TEXT PRIMARY KEY,
  name      TEXT NOT NULL UNIQUE,
  createdAt TEXT NOT NULL,
  updatedAt TEXT NOT NULL
);

CREATE TABLE entityB (
  id        TEXT PRIMARY KEY,
  entityAId TEXT NOT NULL REFERENCES entityA(id),
  payload   TEXT NOT NULL,
  createdAt TEXT NOT NULL
);

CREATE TABLE session (
  handle    TEXT PRIMARY KEY,
  principal TEXT NOT NULL,
  issuedAt  TEXT NOT NULL,
  expiresAt TEXT NOT NULL
);

CREATE TABLE auditEntry (
  id        TEXT PRIMARY KEY,
  actor     TEXT NOT NULL,
  action    TEXT NOT NULL,
  targetId  TEXT NOT NULL,
  at        TEXT NOT NULL
);
```

`migrations/0002_soft_delete_column.sql`:

```sql
-- Soft-delete column on entityA for file-lane removal without eager history loss.
ALTER TABLE entityA ADD COLUMN removedAt TEXT;
```

`migrations/0003_boot_markers.sql`:

```sql
-- Boot markers: audit trail of Worker isolate cold-starts.
CREATE TABLE bootMarker (
  bootAt TEXT PRIMARY KEY
);
```

`migrations/0004_notifier_schema.sql`:

```sql
-- Notifier: per-entity channel routes and pending-delivery queue.
CREATE TABLE entityChannelRoute (
  entityId  TEXT NOT NULL,
  channelId TEXT NOT NULL,
  PRIMARY KEY (entityId, channelId)
);

CREATE TABLE channel (
  id        TEXT PRIMARY KEY,
  isDefault INTEGER NOT NULL DEFAULT 0
);
```

## Applying migrations

The wrangler CLI applies files in ascending leading-integer order:

```
# Local dev
wrangler d1 migrations list  <database> --local
wrangler d1 migrations apply <database> --local

# Preview environment
wrangler d1 migrations apply <database> --env preview

# Live environment (typically run by the CI job before the Worker deploy)
wrangler d1 migrations apply <database> --env live
```

The applied files land in the bookkeeping table (`d1_migrations` by default). A subsequent `list` reports zero unapplied migrations; a `SELECT * FROM d1_migrations` returns one row per applied file.

## Rules a project must not break

- **Leading integers are monotonic and unique across the directory.** A missing integer between shipped files, or a duplicate, breaks the ordering guarantee the wrangler CLI relies on. Two contributors landing overlapping integers is a merge conflict, not a runtime bug.
- **A shipped migration is never edited.** Adding a statement to an already-applied file is a silent schema divergence between deployed databases at different apply cycles. Fixes ship as new numbered files, appended.
- **The bookkeeping table is not the migration's concern.** A migration whose statements include an `INSERT INTO d1_migrations` corrupts the wrangler CLI's ordering; the CLI already handles that insert inside the same transaction as the migration's statements.
- **Statements are D1-flavoured SQLite dialect.** D1 shares SQLite's SQL semantics; statements that assume Postgres-specific features (SERIAL, native JSONB, LATERAL) fail at apply. When switching engines under a superseding ADR-1401, plan for a dialect translation pass.
- **Import from an existing SQLite dump requires stripping `BEGIN TRANSACTION` and `COMMIT`.** The vendor's guidance is explicit: D1's `wrangler d1 execute --file` refuses these statements. A migration file authored from a sqlite3 dump has them removed at authoring time.
