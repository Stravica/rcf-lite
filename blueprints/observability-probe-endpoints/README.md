# Observability probe endpoints blueprint (v1.0.0)

The tenth content blueprint on the rcf-build-lite blueprint mechanism, and the second in the `observability` category, sibling to the shipped `observability-essentials`. Scope: a health probe interface derived from an operator-declared target integration profile (`kubernetes`, `loadBalancer`, `uptimeMonitor`, `systemd`, `dockerHealthcheck`, `reverseProxy`, plus a `custom:<name>` slot). Each profile fixes the probe transport, path or command surface, response contract, and semantic distinction between liveness and readiness for the supervisor at hand. Kubernetes is the shipped default (HTTPGet `/live` and `/ready` on the request-traffic listener); every HTTP profile ships with a `probeListener.separatePort` opt-in for probe-traffic isolation from user traffic. Response contracts are minimal by construction; the profile validator refuses any override that would add a field beyond the enumerated set. Targeted at rcf-lite projects that must integrate with a specific EXTERNAL supervising system whose conventions drive the probe wire shape; not targeted at the self-supervised all-in-one observability case (observability-essentials owns that).

## Apply

```
rcf define blueprint add <path-to>/blueprints/observability-probe-endpoints
```

Phase 1 resolves local path sources only; registry and git-ref resolution is a mechanism follow-up. Apply is idempotent; `rcf define blueprint list` shows the applied entry grouped under the `observability` category; `rcf define blueprint remove observability-probe-endpoints` cleanly removes an unreferenced application.

## What it contributes, and what it deliberately does not

Contributed kinds: REQ, US (with inline ACs), TAC, ADR. Adherence is expressed as ACs; the blueprint ships no test files (ratified decision 5) and no code.

No FBS contributions, as a matter of principle (ratified policy 2026-08-19): FBSs are the work of the implementing agent, not the blueprint; project constraints have to be applied at the time of creation. The blueprint contributes the WHAT (the elicitation surface, the six shipped profile contracts, the two-listener topology option, the auth-exempt-list emission, the response-contract secrecy rule, the profile-swap-is-config invariant); the implementing agent derives the HOW-tasks (FBS) in the host project, where the ACs contributed here get picked up by the project's own build sequencing.

Deliberately not contributed: a public status page (observability-essentials owns `statusPageContract` for that audience); a notification outcome sink (observability-essentials owns that); an authenticated operator dashboard for granular internal state (project-authored on top of the readiness predicate); a metrics-export surface (a future `metrics-export` blueprint composes alongside); a distributed-tracing surface (a future `tracing` blueprint composes alongside); a log-shipping surface (application-api-rest's `logging` topic governs the wire-log shape of the HTTP tier); the readiness predicate implementation itself (project-authored; the blueprint fixes the boundary and each profile's default aggregation rule, not the per-dependency check code); the auth middleware installer (project-authored; the blueprint emits an exact-match exempt list the installer consumes); the vendor-CLI or client-library binding for any supervisor beyond the profile contract (project-authored inside a `custom:<name>` profile).

## The two global decisions

ADR-1501-observability-probe-endpoints-health-probes ships `scope: global` on topic `healthProbes`. This is the project's health probe interface: elicited from the target integration profile, materialised by the profile-resolver into a frozen object that drives every downstream binding. A composing blueprint that holds a different opinion on the health probe interface (observability-essentials's self-supervised two-endpoint HTTP JSON floor is the shipped example; a future metrics-probe hybrid or a health-protocol variant would compose here too) conflicts by design.

ADR-1502-observability-probe-endpoints-readiness-semantics ships `scope: global` on topic `readinessSemantics`. This is the project's readiness aggregation and cadence: elicited per profile so the shape and the flip window follow what the supervising system reads. A composing blueprint that holds a different opinion on readiness semantics (observability-essentials's strict-any-fail-over-declared-deps as the ONE project-wide rule is the shipped example) conflicts by design.

Both ADRs conflict with observability-essentials on the same two topic strings on purpose. See `docs/topics.md` for the exact strings, the four documented resolution paths per conflict, the boundary with observability-essentials's `statusPageContract` (which this blueprint does not touch), and the AC id band allocation (observability-probe-endpoints owns 14101-14899, ADR/TAC suffix block 15xx).

## Quality bar

The probe surface always follows the operator-declared target integration profile; a missing or unrecognised declaration refuses boot with a stable-coded error naming the field. The Kubernetes profile is the shipped default; a bare apply exhibits HTTPGet `/live` and `/ready` on the request-traffic listener with the `{"status":"pass"|"fail"}` body shape and no operator configuration. Each of the six shipped profiles resolves to a config object whose transport, path (or command/notify equivalent), response contract, and semantic model are all present; a partial profile is refused at boot. Every HTTP profile carries a `probeListener.separatePort` opt-in; when set, probe handlers bind to a dedicated listener that serves only the resolved probe path set and no other routes; when unset, probe handlers bind to the user-traffic listener. Response contracts are minimal by construction: HTTP profiles that consume status-only carry content-length zero on every response; HTTP profiles that consume a body emit exactly the enumerated field set (`{"status":"pass"|"fail"}` for Kubernetes and nothing more); the profile validator refuses any override that would add a field beyond the enumerated set. No dependency name, environment name, hostname, replica id, build hash, or commit sha ever appears on any external-visible probe response. The auth-exempt list emitted by the topology component is exact-match scoped to the resolved probe path set on the resolved listener; a wildcard or prefix matcher is refused. Switching profiles is a configuration change; the source tree carries no per-profile conditional outside the profile modules and the profile-resolver. Every bar is carried by ACs in the doc set, not by this README.

## Known mechanism-reach gaps

- **Custom-profile contract adherence.** Projects that author a `custom:<name>` profile against the profile contract are expected to satisfy the same transport/paths/responseContract/semanticModel shape the shipped profiles do; the profile contract validator (TAC-1501) refuses a partial profile at boot, which is where the mechanism reach lands. What the validator cannot compel is that a project-authored custom profile's response shape is minimal in the AC-14105 and AC-14106 sense (a custom profile could in principle enumerate a rich field set the validator would accept as complete). Recorded here rather than smuggled in as an AC that would only apply to the shipped profiles. Promotion signal: a `custom-profile-shape-lint` addition to the profile contract validator that enforces the minimalism rule per field-set-size heuristic (harder than it sounds; some legitimate custom profiles do have wider fields); or a project-side grep gate. Project-side workaround until then: reviewers of a `custom:<name>` profile eyeball the enumerated field set against the pattern the shipped six carry.
- **Kubernetes gRPC probe transport.** The `kubernetes` profile ships HTTPGet and TCPSocket transports (via TAC-1504's tcpAdapter selection) but not gRPC. A project on a gRPC-only mesh that wants the standard gRPC health protocol supersedes ADR-1503 with a project-level ADR selecting the gRPC transport, or authors a `custom:kubernetes-grpc` profile. Promotion signal: a shipped gRPC-transport handler in a v1.1 pass if enough rcf-lite projects reach for it. Project-side workaround: the `custom:<name>` slot is the mechanism escape hatch.
